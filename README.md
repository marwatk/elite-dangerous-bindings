# Elite Dangerous Bindings

A browser-based tool for exploring, **editing** and printing your **Elite Dangerous** control bindings. Load your `.binds` file (or start from scratch) and you get:

- a **searchable bindings table** showing every command, with your controller's real button names,
- a **bindings editor** where you **bind a command by pressing the actual button or moving the actual axis** on your HOTAS, pedals or keyboard, and then **export a working `.binds` file**, so you don't have to use the in-game controls menu, and
- a **printable graphical reference card** that draws each command onto a picture of your joystick, HOTAS, pedals, gamepad or keyboard.

Everything runs in your browser. Your bindings file is never uploaded to a server.

**Use it now: [marwatk.github.io/elite-dangerous-bindings](https://marwatk.github.io/elite-dangerous-bindings/)** (Chrome or Edge recommended for reading controllers directly).

## Features

### 1. Loading bindings

- **Open or drag and drop** a `.binds` file. No install and no upload are needed; the file is parsed in the browser.
- **Tips for finding your file**, with the default Windows path: `%LOCALAPPDATA%\Frontier Developments\Elite Dangerous\Options\Bindings`.
- **Supports all game versions**: Horizons and Odyssey bindings, including On Foot, Multicrew, Fighter, SRV, Holo-Me, the Store camera and the FSS scanner.
- **Shows file metadata**: the preset name, game version and keyboard layout (for example `en-US`) stored in the file.
- **Remembers recent files** in browser storage (optional, stays on your device), so you can reopen your bindings without picking the file again.
- **Clear parse errors** if the file is malformed or is not a bindings file.

### 2. Bindings table (from EdBindings)

A fast, filterable table built with Angular Material (`mat-table`) that lists every command:

| Column | Description |
| --- | --- |
| Area | For example *Ship Controls*, *SRV Controls*, *On Foot*, *Galaxy Map* |
| Category | For example *Flight Rotation*, *Weapons*, *Interface Mode* |
| Action | A readable command name (for example `UI_Up` → "UI Panel Up") |
| Primary device / control | The physical device and a friendly button label (for example *Throttle / Left Dial Forward* instead of `SaitekX56Throttle / Joy_30`) |
| Secondary device / control | The same, for the secondary binding |
| Modifiers | Any modifier or "hold" keys needed for the binding |
| VoiceAttack / bindED variable | The variable name used by [bindED](https://github.com/alterNERDtive/bindED), for example `edUI_Up`, with a copy-to-clipboard button |

Table features:

- **Instant text filter** that searches action, area, category and bound controls.
- **Facet filters**: area, category, device, and "bound / unbound / conflicting".
- **Sortable columns**, column show/hide, and paging or virtual scrolling for large files.
- **Friendly control labels** from the unified device definitions (see §6). If a device isn't supported, the raw code is shown.
- **Conflict detection** flags when the same physical control (with the same modifiers) is bound to more than one command in the same context.
- **Export** the table (filtered or complete) to CSV.

### 3. Binding with your real controls (new; neither upstream tool can do this)

Both EdBindings and EDRefCard are read-only. The main reason this project exists is to bind commands by using your hardware: select a command, then press the button, flick the hat or move the axis you want to use for it.

**How input is read**

The browser reads controllers through two interfaces. Both are handled behind a single input layer, so the rest of the app doesn't need to know which one is in use:

| | WebHID (preferred) | Gamepad API (fallback) |
| --- | --- | --- |
| Browsers | Chrome, Edge, Opera | All modern browsers |
| Permission | You pick each device once in the browser's dialog; it is remembered | None, but a device only appears after you press one of its buttons |
| Device identity | Exact USB vendor/product ID | Parsed from the gamepad name string, which differs between browsers |
| Control numbering | Taken from the device's own HID descriptor: button usage *N* → `Joy_N`, X/Y/Z/Rx/Ry/Rz/Slider/Dial → `Joy_XAxis` … `Joy_UAxis`/`Joy_VAxis`, hat switches → `Joy_POVn*` | Taken from the browser's index order, which usually matches the game but not always |
| Limits | None known | At most 4 controllers; hats often reported as a strange axis value; large devices are split into 32-button groups |

The app uses WebHID for every device you have granted it, and the Gamepad API for everything else. The same physical device is never read through both at once.

**Capture**

- **Buttons and hats**: a press is detected when a button goes from released to pressed. Hat directions become `Joy_POV1Up`, `Joy_POV1Right`, and so on.
- **Axes**: a resting position is recorded first. Movement past a threshold then counts as selecting that axis, so noisy or drifting axes don't trigger by themselves. The direction you moved it in is recorded, so for axis-half commands you get `Pos_`/`Neg_` versions and for normal axis commands you get an *Inverted* suggestion.
- **Modifiers**: to capture a combination, hold one or more controls and press another. The held controls become `<Modifier>` entries, from the same or a different device.
- **Keyboard**: browser key codes are mapped to Elite's `Key_*` names, including left/right Ctrl/Shift/Alt and the numpad. The keyboard layout stored in the file is taken into account.
- **Device IDs**: the USB vendor/product ID is converted to the ID Elite writes in the file. That is either the 8-digit hex form (`231D0200`) or one of the game's named IDs (`SaitekX56Joystick`, `T16000M`, …). If the file already contains a binding for the same device, the ID and `DeviceIndex` from the file are used, so they always match.
- **Confirm before saving**: the captured control is shown with its label and position on the device picture. You confirm it, or pick a different control from a list.

**Tools for your controllers**

- **Live input view**: move anything on any connected controller and see it light up on the device picture, together with the commands it is currently bound to. It also answers "what does this button do?"
- **Numbering check**: the app asks you to press a few controls that are already bound in your file. If the browser's numbering disagrees with the game's, you get a warning, and a correction (for example a button offset or a swapped axis) is saved for that device.
- **Diagnostics panel**: shows raw input, detected devices, which interface each one is using, and devices in your file that aren't currently connected.

### 4. Editing and export

**Editing**

- **Edit any command** from the table or by clicking a control on the reference card. You can set:
  - Primary and secondary bindings for buttons and keys (device + control), or the single axis binding for analogue commands.
  - Modifiers (one or more keys or buttons that must be held), and the *Hold* flag.
  - Per-command options: *Toggle On*, *Inverted* and *Deadzone*.
  - Global settings stored in the file, such as mouse mode and sensitivity, yaw-into-roll, and throttle settings.
- **Three ways to choose a control**:
  - Press it on the device (§3).
  - Click it on the controller picture.
  - Pick it by name from a list ("Throttle › Left Dial Forward").
- **You choose the slot.** You decide whether a capture goes into the primary or the secondary binding. An existing binding is only replaced after you confirm.
- **Existing settings are kept.** Rebinding an axis keeps its current *Inverted* and *Deadzone* values.
- **Live conflict checking** while you edit. You are warned when a control is already used in the same context. Contexts are taken into account, so the same button can be used for a Ship command and an On Foot command without a warning.
- **Validation**: axis commands only accept axes, and button commands only accept buttons, keys or hat directions. Digital commands bound to an analogue axis (see §7) are flagged.
- **Bulk operations**:
  - Clear every binding for a device.
  - Move a device's bindings to a different device ID. This helps when identical hardware shows up with a different ID on a new PC, or when you replace your stick.
  - Copy a set of commands to another context, such as Ship → SRV.
- **Undo/redo** and a **change list** that shows every difference from the file you loaded, with a way to revert each change.

**Starting points**

- Edit an existing custom `.binds` file.
- Start from an **empty preset**. It contains every action (about 420 in Odyssey 4.2) with nothing bound, in the order the game writes them.
- Start from Frontier's **default presets** (Keyboard, Xbox, DualShock 4, X52, X56, Warthog, and others), if their licensing allows it (see [docs/prior-art.md](docs/prior-art.md)).
- **Merge** bindings from another file, for example to take someone's SRV bindings but keep your ship bindings.

**Export**

- **Lossless round-trip**: the file you loaded is kept as an XML document and edited in place. Unknown elements, attributes and settings, including ones from future game updates, are kept unchanged. The file's formatting also matches what the game writes: tab indentation, line endings, the `<?xml … ?>` header, and numbers such as `0.09000000`. Loading a file and exporting it with no edits produces an identical file, and automated tests check this against real files.
- **Preset naming**: choose the preset name and game version (Horizons `3.0` / Odyssey `4.0`–`4.1`). The file is named to match, for example `MyHOTAS.4.1.binds`.
- **Download**, or **save directly** into your Bindings folder using the File System Access API in Chromium browsers (with confirmation before overwriting). A timestamped backup of the original file is made before saving.
- **Export custom button names**: generate `DeviceButtonMaps/*.buttonMap` files for the controls you've labelled, so your own names appear in the game's controls menu and on-screen prompts. This uses the [EliteCustomButtonNames](https://github.com/EDCD/EliteCustomButtonNames) format.
- **Instructions for installing the file**: quit the game first (or it may overwrite your changes), where to copy the file, and how to choose the preset under *Options › Controls*.

### 5. Graphical reference cards (from EDRefCard)

- **Overlay commands on controller artwork.** Each bound command is drawn next to its button, hat, axis or key on a picture of the device. Cards are rendered in the browser as **SVG**, so they stay sharp at any zoom and print cleanly.
- **Keyboard card** with key symbols for the physical keys that are bound.
- **Category filters** control which command groups appear on the card: Ship, SRV, Scanners, Fighter, On Foot, Multicrew, Head Look, UI, Galaxy Map, Camera, Holo-Me and Miscellaneous.
- **Colour schemes**:
  - *By modifier*: each modifier and its modified commands share a colour.
  - *By type/category*: General, Combat, Social, Navigation and UI each get a colour.
  - *By group*: Ship, SRV, Galaxy Map and so on each get a colour.
  - *No colours*: plain print.
- **Modifier support**: numbered modifiers, combined (multi-key) modifiers, and the "Hold" option are all shown on the card.
- **Hides redundant specialisations.** For example, *GalMap Pitch* is not repeated if it uses the same axis as the regular Pitch.
- **Short labels** (for example "FSD" and "GEAR") for common commands, so busy buttons stay readable.
- **Best-fit text sizing** so that many commands on one button still fit in its label box.
- **Multiple identical devices**, such as dual sticks, are handled with device indices.
- **Print and export**: print-optimised layout (one device per page), and download as PNG, SVG or PDF.

### 6. Supported devices

- **60+ controllers** from EDRefCard, including Thrustmaster (Warthog, T.16000M/FCS, TCA, HOTAS X/4/One, Cougar, TFRP/TPR pedals), Logitech/Saitek (X45, X52, X52 Pro, X55, X56, G940, Extreme 3D Pro, pedals, FLY 5), VKB (Gladiator, Gladiator NXT/EVO, Kosmosima, STECS), Virpil (Alpha, Alpha Prime, WarBRD DELTA, Constellation, MongoosT throttles, Control Panel 2), WinWing (Orion 2, Ursa Minor), CH Products, Xbox/Xbox Elite, DualShock 4, Logitech F710, and others.
- **Unified device definitions**: one JSON file per device holds:
  - the USB vendor/product ID and the device IDs used in `.binds` files,
  - the artwork, and the position of each control on the artwork,
  - a friendly label for each control, and
  - any browser-numbering corrections for live input.

  The table, the editor, live input and the reference cards all use the same data. It combines EDRefCard's *hotasDetails* layouts, EDCD's button-name maps and EdBindings' device mapping files.
- **Unknown devices still work** for editing and live input, using a generic inventory: 32+ buttons, 8 axes and their halves, and 4 hats. They just have no artwork.
- **Device browser**: a list of every supported device and its handled device IDs. For each device you can open a **layout debug view**, which draws every control's label box on the artwork. This helps when adding or fixing a device.
- **Contributor-friendly**: a device is added with a JSON file and an image in a pull request, without changing any code. The format is documented in the repo.

**Device layout editor (add a new controller)**

If your controller isn't supported, you can map it yourself from a picture. You then export files that can be added straight to this repo.

1. **Provide an image.** Upload a photo, render or diagram (PNG, JPG, SVG or WebP) and crop or straighten it in the editor. You can use more than one image for multi-part devices, such as a stick and throttle, or the front and back of a grip.
2. **Identify the device.**
   - Connect it and press any button. The USB vendor/product ID is read through WebHID or the Gamepad API and converted to the ID Elite writes in `.binds` files.
   - Or pick the ID from a loaded `.binds` file, or type it in.
   - You can add extra IDs, for example for other hardware revisions or a named ID.
3. **List the controls.**
   - With WebHID, the full list of buttons, axes and hats is read from the device itself, so nothing gets missed.
   - Otherwise it builds up as you press controls, or starts from an EDCD `.buttonMap` for the device if one exists, or from the generic template.
4. **Place each control.**
   - Press a button or move an axis on the real device, then click or drag on the image to draw its label box. The editor then moves to the next unplaced control.
   - You can also select a control from the checklist and draw its box.
   - Label boxes can be moved, resized and aligned. Snapping and "same size as" help keep columns of labels tidy.
   - Several controls can share a box, for example an axis and its two halves, or a hat's four directions shown as a group.
5. **Name the controls.** Give each control a friendly label ("Pinky trigger", "Hat 2 Up"), and optionally one of Elite's icon tokens (for example `[x52prox]`) for use in-game.
6. **Check it.**
   - Live preview: pressing a control highlights its box.
   - A test card is rendered using your loaded bindings, or with filler text to check that dense labels still fit.
   - Validation lists controls with no box, overlapping or off-image boxes, duplicate labels and missing IDs.
7. **Export.** A `.zip` in the repo's folder layout, ready for a pull request:
   - `devices/<device-id>/device.json`: the device definition (IDs, controls, types, labels, box positions scaled to the image, numbering corrections).
   - `devices/<device-id>/<name>.webp` (or `.svg`): the artwork, resized to the standard card size.
   - `buttonmaps/<device-id>.buttonMap`: EDCD-format labels for the game, not for the repository. Copied into Elite's `Options\Bindings\DeviceButtonMaps` folder, they make the game show your names; they can also be sent upstream to EliteCustomButtonNames. The zip's readme explains both.
   - A short `CONTRIBUTING` note with the steps for opening the pull request, and a reminder to use only images you have the right to share, such as your own photo.

A device you have mapped **can be used straight away** in your browser without waiting for it to be merged. It is saved locally and can be exported and imported as a `.zip`. The same editor opens existing devices, so you can **fix or improve** a layout that's already in the repo and export only the changed files.

### 7. Diagnostics and warnings

- **Unknown controller**: names the device IDs in your file that are not supported yet, and links to instructions for contributing a device definition.
- **Misconfigured analogue controls**: detects digital commands bound to analogue axes (a common Elite configuration mistake) and lists the affected commands.
- **Mapping software detected**: warns when Thrustmaster TARGET's combined virtual device is in use, because some controls may not appear.
- **No supported bindings**: explains when a file has no bindings for any supported controller or keyboard.

### 8. Sharing

- **Shareable links**: the bindings are compressed into the URL fragment, so you can share a link to your reference card and table without a server storing anything.
- **Download the `.binds` file** from a shared link so others can use the same configuration.

A public gallery of published configurations (like the EDRefCard `/list` page, searchable by controller) needs a backend. It is **out of scope for the first release** and may be added later as an optional service.

### 9. General

- Built with **Angular** and **Angular Material**, in a light or dark theme with an Elite-style orange accent.
- Responsive layout that works on both desktop and tablet.
- Installable **PWA** that works offline after the first visit.
- Can be hosted as a static site, for example on GitHub Pages.

## Architecture

| Concern | Choice |
| --- | --- |
| Framework | Angular (standalone components, signals) |
| UI | Angular Material + CDK (table, virtual scroll, drag and drop) |
| Parsing | `DOMParser` on the `.binds` XML, turned into a typed binding model |
| Data | Static JSON: action/command metadata (converted from EdBindings `ActionMappings.json` and EDRefCard `controlsData.py`) and one file per device (converted from EDRefCard `bindingsData.py` and EdBindings `DeviceMappings`) |
| Card rendering | SVG, generated in the browser on top of each device's artwork |
| Export | Browser print CSS; SVG → PNG through a canvas; PDF through a client-side library |
| Editing | The loaded XML document is edited in place and saved with `XMLSerializer`, so nothing is lost on export |
| Input capture | One `InputSource` interface with two back ends: **WebHID** (reads the HID report descriptor through `device.collections`; preferred) and the **Gamepad API** (fallback). Both produce the same event: device, Elite control name, value. `KeyboardEvent.code` → `Key_*` for keys |
| Device data | `devices/<device-id>/device.json` + artwork, validated against a JSON Schema in CI; the app loads them through a generated index. The layout editor exports exactly this format |
| Persistence | `localStorage`/IndexedDB for preferences, recent files and unsaved edits |
| File saving | Download, or save in place with the File System Access API (Chromium) |
| Hosting | Static files; no server-side code |

## Development

All development runs inside an [Apple container](https://github.com/apple/container), so nothing needs installing on your Mac apart from the `container` CLI.

```sh
tools/dev.sh                 # start the dev container and the dev server at http://localhost:4200
tools/dev.sh npm test        # unit tests (Vitest)
tools/dev.sh npm run e2e     # end-to-end tests (Playwright + Chromium, in the container)
tools/dev.sh npm run shots   # screenshot tooling for visual checks -> test-results/shots/
tools/dev.sh npm run build   # production build in dist/
tools/dev.sh shell           # shell inside the container
```

| Path | What's there |
| --- | --- |
| `src/app/core/binds/` | Lossless `.binds` reader/writer. Editing a file and saving it changes only the lines you edited. |
| `src/app/core/input/` | Live input: WebHID, Gamepad API and keyboard, reported in Elite's naming |
| `src/app/features/` | The pages: bindings table and editor, reference cards, live input, devices and layout editor |
| `devices/<id>/` | One folder per controller: `device.json` + artwork. See [docs/adding-a-device.md](docs/adding-a-device.md) |
| `schemas/device.schema.json` | Schema every `device.json` is checked against (`npm run devices:check`, also in CI) |
| `public/data/` | Action catalogue, key names, device IDs, empty template |
| `tools/` | Data import from the upstream projects (`npm run import-data`), device index builder, dev helper |

The data in `public/data/` and `devices/` was generated by `tools/import_data.py` from the upstream projects, pinned in `tools/upstream.lock`.

## Status

All the features above are built, apart from these gaps:

- **Copying commands between contexts** (Ship → SRV) is not built: there's no reliable one-to-one mapping between the actions.
- **Live input hasn't been tested with real controllers** yet, only with simulated ones in automated tests. Button, axis and hat numbering may need per-device corrections; the numbering check on the Live input page is there to find and save them.
- **Shareable links** carry the whole file in the URL. There is no public gallery.
